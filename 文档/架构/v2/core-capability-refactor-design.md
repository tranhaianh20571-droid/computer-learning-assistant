# 学习助手伙伴：PydanticAI 原生执行与 Capability 重构设计

> **文档性质：目标架构与迁移方案，不代表重构或监控平台已实现。**
>
> 保留模块化单体、现有业务行为与数据安全边界。以 PydanticAI Core 承接 AI 执行链，由 SDK 负责模型循环、消息历史、工具执行、输出校验重试与原生流式事件；Capability 提供可组合行为，原生 Model / Provider 处理供应商协议，业务服务保留授权、任务与提交权。
>
> 监控采用 **PydanticAI → 原生 Instrumentation → OpenTelemetry → Logfire**。本文不记录部署地址、供应商端点、依赖版本、配额数值或重试次数。图表为纯文本和 Markdown 表格，可独立离线阅读；运行时组件依赖不等于文档渲染依赖。

## 1. 设计总览

**核心原则：SDK 承担 AI 执行机制，业务服务掌握权限、任务与提交，Capability 提供受控行为，原生 Model / Provider 处理协议。**

```text
用户操作 -> HTTP / SSE -> 业务编排 + 持久任务
                                  |
                                  v
                         类型化 Agent 接口
                                  |
                                  v
                       PydanticAI 原生执行机制
                       +-- Agent：循环、消息、工具、输出修复
                       +-- Capability：上下文、工具、运行策略
                       +-- Instrumentation：原生运行观测
                                  |
                                  v
                       原生 Model / Provider / Profile
                                  |
                                  v
                       受控客户端 + 最终安全出口
                                  |
                                  v
                               供应商

完整运行的最终候选 -> 领域校验 -> 事务围栏 -> 保存与发布
搜索 / OCR / TTS / 图像 -> 独立服务路径 -> 同样受安全出口约束
```

| 层级 | 负责 | 不负责 |
| --- | --- | --- |
| HTTP / 事件接口 | 解析请求、认证、响应投影、断线重建 | 拼装模型循环、决定评分 |
| 业务编排与持久任务 | 状态迁移、版本与租约、预算、保存与恢复 | 依赖提示词保护权限 |
| 类型化 Agent | 声明角色、输入、输出、可用能力 | 任意选择输出类型、直接提交业务结果 |
| PydanticAI Core | 模型循环、原生消息、工具执行、输出校验重试与流式事件 | 承担应用的事务与资源授权 |
| Capability | 组合指令、工具、上下文与运行策略 | 替代领域服务、绕过安全出口 |
| Model / Provider / Profile | 分别处理协议、连接与认证、模型能力及 Schema 兼容性 | 自动保证应用授权、出口安全或多租户隔离 |
| 受控客户端与安全出口 | 实际载荷与目的地校验、凭据隔离、连接生命周期、受控错误 | 自动扩大授权或切换供应商 |
| 领域服务与存储 | 业务不变量、提交围栏、不可变版本 | 将未完成流式内容当作正式结果 |

**命名澄清：** 本文的 PydanticAI Core 指 SDK 已有的执行机制，不是新建一个自定义 `Core` 类、Runner 框架或 `pydantic-core` 校验引擎。现有应用 `core` 建议改名为 `infrastructure`，保留配置、数据库和安全职责；目录迁移不能代替执行职责迁移。供应商能力状态与 SDK Capability 分开管理；不引入通用代码执行、Shell 或文件系统能力。

## 2. 当前结构与重构重点

当前主链路是：**业务 Service → 角色包装器 / 通用 Runner → PydanticAI Agent → FunctionModel 桥接 → 自有供应商适配器**。后台任务由应用进程内调度，不能把它描述成已部署的独立 Worker 集群。

| 当前结构或审查发现 | 目标变化 |
| --- | --- |
| 已使用 PydanticAI，但角色接口允许自由传入输出类型和参数，尚未按 SDK Capability 统一装配 | 角色固定契约，共享行为由 Capability / Hook 组合 |
| 生产 FunctionModel 桥重复转换消息、工具与流式响应 | 已支持协议优先使用官方 Model / Provider；撤除重复协议转换 |
| 外层 Runner 重复输出修复，消息裁剪不能完整保留工具与重试语义 | 由 SDK 执行输出重试并保留原生 ModelMessage 历史，应用仅管理业务预算和状态 |
| 校验分散在字段、输出校验器和返回后的 Service 中 | 纯规则复用，明确可回喂校验与提交校验 |
| 普通路径、流式路径和聊天旧路径存在上下文与工具接线差异 | 共用上下文装配、预算、安全出口与错误分类 |
| 检索默认正文读取、真实搜索和 OCR 装配存在缺口 | 显式声明可用能力；未装配不视为成功接通 |
| 讲次规划角色已定义，但常规教学主要使用已保存、预备或本地轻量蓝图 | 明确后台细化与首段轻量路径，保留已冻结内容 |
| 输出校验失败可能影响能力失败缓存 | 将内容不合格与协议不支持分开处理 |
| 任务围栏、外发范围和事件事务存在待补齐项；部分审计失败被吞掉 | 用服务端硬校验与事务契约补齐，不能仅搬进 Hook |

**FunctionModel 并非禁止用于生产。** 官方主要将其用于测试与开发；本项目迁移它的理由是已有官方协议实现，自建桥重复处理消息、工具与流式响应，增加维护成本及信息丢失风险。特殊协议确有必要时可实现自定义 Model，但必须完整支持所需的消息、工具、流式与用量语义，不能继续用文本桥代替。

**重构不是更换包装层。** SDK 接管执行后，仍须证明真实上下文进入请求、安全校验覆盖所有出口、任务结果与事件一致提交。

## 3. Agent 接口与能力组合

### 3.1 固定角色接口

以下为**建议契约**。方法名与输入模型属于目标定义；不能误认为这些方法已经存在。

统一调用形态：`角色方法(业务输入, 可信依赖) -> AgentResult[候选类型]`。

| 角色 | 建议方法 | 输入 → 候选输出 | 主要能力 |
| --- | --- | --- | --- |
| 学习访谈 | `interview` | `IntakeInput` → `IntakeQuestionSet` | 访谈历史、学习者背景、范围澄清 |
| 课程规划 | `generate_route` | `RoutePlanningInput` → `RouteCandidate` | 选材检索、可选搜索、路线规则 |
| 课程规划 | `generate_outline` / `refine_outline` | `OutlinePlanningInput` → `OutlineCandidate` | 课程骨架、选材检索、大纲规则 |
| 讲次规划 | `plan_lesson` | `LessonPlanningInput` → `LessonBlueprint` | 目标与教学上下文、蓝图规则 |
| 教学 | `generate_step` | `TeachingStepInput` → `StepCandidate` | 当前阶段、板书上下文、步骤规则 |
| 教学 | `answer_followup` | `FollowupInput` → `FollowupCandidate` | 当前讲次与已发布内容 |
| 单元测验 | `generate_assessment` | `AssessmentInput` → `UnitAssessment` | 单元学习上下文、题目完整性 |
| 答案评估 | `evaluate_answers` | `EvaluationInput` → `AssessmentFeedback` | 服务端客观题评分、开放题评价 |

辅助功能独立定义输入输出：规划对话、规划修订、封面候选和普通聊天。**聊天输出文本，修订输出操作候选，封面输出资源候选；不能混成一个无约束接口。**

`AgentResult[T]` 是建议的应用候选封装，不是 SDK 类型；可由 SDK `AgentRunResult[T]` 提取通过生成阶段校验的候选、输出模式、降级原因和必要的运行元数据。两者都不代表事务提交成功，不是数据库记录。消息历史保留 SDK 原生 `ModelMessage` 的助手、工具调用与返回、重试信息及必要的供应商元数据，不先压平成文本；仅在受控业务存储中使用，不进入通用日志。

### 3.2 可信依赖与上下文

```text
业务输入：目标、问题、答案、资源引用
                 |
                 v
服务端授权解析 + 版本绑定
                 |
                 v
可信 Deps：主体、范围、版本、任务上下文、共享预算、窄服务接口
                 |
                 v
上下文装配：历史 + 选材片段 + 当前业务快照
                 |
                 v
预算裁剪 + 实际载荷清单
                 |
                 v
Agent[Deps, Output] / RunContext[Deps]
```

- `Deps` 使用类型化容器；工具只得到所需的窄接口，不获得完整 Service 或任意数据库操作权。
- 用户或模型提交的资源 ID 必须由服务端解析和授权。声明 `deps_type` 本身不提供运行时数据校验。
- 实际载荷清单与最终请求保持一致，只记录受控引用和元数据，不复制正文进入日志。
- 后台执行重新核验授权与状态；启动任务时的快照不能替代调用时校验。
- 多租户不得共享可变的 API 凭据、默认请求头或基础地址；客户端按租户、目的地和凭据版本隔离复用，由应用负责关闭自己创建的客户端。

### 3.3 Capability 的职责边界

| 类别 | 组合内容 | 关键边界 |
| --- | --- | --- |
| 上下文能力 | 历史处理、选材检索、教学上下文、提示词快照 | 只读取授权范围内数据 |
| 业务工具能力 | 搜索、修订候选校验、测验上下文、客观题评分 | 参数与返回值有 Schema；模型不能任意改分或直接提交 |
| 运行策略能力 | 预算、模型选择策略、请求前检查 | 全任务共享限制，不因降档重置；不重复实现 SDK 输出重试与事件协议 |
| 观测能力 | 原生 Instrumentation 及必要的受控元数据 | 不重复埋 Agent / Model / Tool Span；业务埋点独立补齐，无正文默认采集 |
| 安全能力 | 请求前状态检查、授权核验、敏感内容规则 | 始终启用，不能延迟加载或被调用方覆盖 |

简单组合使用 `Capability`；需复用运行 Hook、模型设置或独立状态时使用 `AbstractCapability`；局部应用行为可使用 `Hooks`，不必全部创建新类。

**组合规则：** 每次运行隔离可变状态；明确声明 Hook 顺序，不能把 `requires` 当作排序。普通工具 Hook 不自动覆盖输出工具；输出校验单独处理。SDK Hook 之外仍保留适配器最终安全出口，覆盖未经过 Agent 的外发调用。

## 4. BaseModel、Schema 与四层模型

**BaseModel 定义可解析的数据形状；JSON Schema 向模型表达结构；二者都不能独立证明业务合法。**

```text
HTTP DTO
   |  接受用户输入，不能信任身份与资源归属
   v
Agent Candidate（Pydantic BaseModel）
   |  模型输出，结构合格不等于允许生效
   v
Domain Verified Value
   |  满足业务规则，提交时仍需检查最新状态
   v
Public Response
      按访问者权限投影，隐藏内部字段与评分秘密

数据库模型独立承载持久化，不直接充当 Agent 候选或公开响应。
```

| 模型层 | 主要内容 | 校验方式 |
| --- | --- | --- |
| HTTP DTO | 操作参数、资源引用、用户文本 | 字段解析与入口约束 |
| Agent Candidate | 路线、大纲、教学步骤、蓝图、测验和评价 | `BaseModel`、字段约束、判别联合、模型校验器 |
| Domain Verified Value | 合法层级、引用关系、目标覆盖、授权版本绑定 | 纯领域规则与服务端上下文校验 |
| Public Response | 当前用户允许看到的结果 | 显式字段投影；测验不泄露标准答案、评分细则和解析 |

模型设计遵循以下规则：

- 新候选明确采用 `extra="forbid"`，拒绝未声明字段；旧数据通过版本化读取兼容，不对存量格式一刀切。
- 枚举用 `Literal` / Enum，板书类型用判别联合；列表数量与元素约束分别定义。
- `strict` 按字段和 Python / JSON 输入语义选择，避免合法历史数据被意外拒绝。
- 配额与预算由统一策略提供，并让生成提示、有效 Schema、领域校验使用同一规则源，不在多处重复写数值。
- `Pydantic strict` 与供应商结构化输出的 strict 是不同机制；供应商保证不能代替本地校验。

## 5. 校验流程与不可越过的边界

### 5.1 四道校验

```text
模型候选
   |
   v
[1] 字段与结构校验
   |  类型、枚举、数量、判别联合、跨字段一致性
   v
[2] 输出校验器 + 纯领域规则
   |  可修正内容问题 -> ModelRetry -> 共享预算内重新生成
   v
[3] 服务端领域校验
   |  所有权、授权范围、引用归属、版本与当前状态
   v
[4] 事务内提交校验
   |  最新租约、取消、期限、墓碑、幂等与版本冲突
   v
原子保存业务结果 + 任务状态 + 任务事件
```

| 检查主题 | 关键约束 | 失败处理 |
| --- | --- | --- |
| 路线与大纲 | 层级与总量、先修引用、无环关系、标题与目标 | 可修正生成错误回喂；提交仍复核 |
| 教学蓝图与步骤 | 阶段顺序、目标覆盖、段落差异、板书引用与展示一致性 | 可修正错误回喂；不提前结束或覆盖冻结内容 |
| 测验与评估 | 题目集合完整、分数边界、客观题程序评分不可改写 | 不合格结果不发布，不伪造评价 |
| 资源与授权 | 主体、资源归属、范围、授权有效性、配置版本 | 直接拒绝，不要求模型“修复权限” |
| 任务与提交 | 任务代、尝试标识、租约令牌、持有者、有效期、取消与总期限 | 丢弃迟到结果，不允许复活 |
| 版本与删除 | 乐观锁、不可变确认版本、删除墓碑、恢复核验 | 冲突拒绝；恢复核验通过前保持锁定 |

路线层级为 `路线 → 阶段 → 课程 → 单元 → 讲次`。课程数与讲次数分别计数；单门课程和整条路线的讲次上限必须显式区分范围，不能仅凭字段名称猜测。

**可回喂的是内容错误，不是安全错误。** 取消、授权撤销、资源删除、租约失效、版本冲突及期限耗尽不得变成 `ModelRetry` 或成功降级。输出校验器保持无提交副作用；最后一次校验以事务中的最新状态为准。

### 5.2 最终外发安全出口

所有模型、搜索、OCR、语音和图像请求都要经过同一安全原则，而不只是 Agent 入口：

```text
最终载荷 + 实际目的地 + 当前配置版本
                    |
                    v
主体与资源归属 / 外发类别与范围 / 撤销与过期 / 当前任务状态
                    |
                    v
允许发送，或受控拒绝并记录审计
```

改变供应商或目的地必须重新满足授权条件。提示词、工具说明和 Capability ID 都不能充当授权凭据；校验通过到实际发送之间应尽量缩小状态变化窗口。

**原生 SDK 不自动保证出口安全与多租户隔离。** 应用负责目的地允许名单、SSRF 防护、DNS 与重定向限制、代理策略、外发范围、凭据隔离与脱敏。安全出口覆盖最终实际请求及每次底层重试，不能仅在 Agent 启动时检查一次；Profile 只描述模型能力与 Schema 兼容性，不承担上述安全职责。

## 6. 输出模式、重试与降级

### 6.1 输出与重试分开设计

默认结构化路径不把模式降档写死为一条固定链：根据 Profile、实际协议支持和业务策略选择 `NativeOutput`、带明确名称的 `ToolOutput` 或 `PromptedOutput`。`NativeOutput` 仅在真实 Model / Provider 完整支持时启用；`ToolOutput` 由 SDK 负责输出工具流程；`PromptedOutput` 依靠提示词要求结构并执行本地校验。不能因 SDK 存在某个输出类型就认定当前协议链路支持。

**模式降档不等于换模型或换供应商。** 输出工具名显式声明；它不是 HTTP 路由，也不是普通业务工具。生产路径应优先使用官方 Model / Provider，不再用 FunctionModel 作为协议转换桥。只有特殊协议无法由官方 Model 表达时，才实现完整的自定义 Model。

**重试分层：** SDK 负责 Agent 的工具和输出重试；Provider / transport 负责协议层尝试；业务服务负责持久任务重试、总预算、取消和 deadline。各层必须共享任务预算，避免重试相乘。Schema 校验失败不自动触发供应商切换；供应商切换必须重新完成授权与外发检查。

| 失败类别 | 策略 |
| --- | --- |
| 字段或业务内容不合格 | 在剩余预算内回喂具体、安全的校验问题；不得缓存成“能力不支持” |
| 协议或输出模式不支持 | 按已批准模式降档，并更新对应配置版本的能力状态 |
| 网络、限流或服务暂态异常 | 按统一策略有限重试，不任意触发输出模式切换 |
| 认证、授权、安全或任务失效 | 立即终止对应操作，不转换为成功结果 |
| 总预算或期限耗尽 | 停止请求，保留已确认结果和可恢复状态 |

请求、工具、输出修复、模式降档及后台重试共用**全任务预算**。SDK 逻辑请求限额之外，还要约束适配器底层网络重试、实际请求数与总耗时，避免多层重试相乘。

### 6.2 各功能的降级边界

下表是应保留或明确落实的目标策略，不是每项都已接通。

| 功能 | 允许的降级 / 回退 | 不允许 |
| --- | --- | --- |
| 学习访谈 | 保存有效历史，失败可重试或恢复 | 凭空补齐用户经历或规划范围 |
| 联网搜索 | 无配置显式标记离线；已配置但失败时等待重试或明确离线继续 | 将失败包装为联网成功 |
| 资料检索 | 标记不可用片段与截断；在已授权、已提供信息内继续 | 声称读取了未装配正文的资料 |
| 课程细化 | 保留骨架和已成功课程，失败部分单独恢复 | 覆盖全部有效结果或报全量成功 |
| 讲次规划 | 已有 / 预备蓝图优先；必要时本地轻量首段；首段发布后独立 `lesson_plan_refine` 任务细化未来会话缓存 | 迟到细化覆盖当前已冻结蓝图或已发布内容 |
| 教学与追问 | 保留已发布内容；新生成失败明确呈现 | 用伪造讲解掩盖失败 |
| 测验与评估 | 客观题分数由程序确定；模型失败保留提交记录 | 将客观评分可计算误称为整条评估流程无需模型；伪造开放题评价 |
| 语音 | 文本继续可用，语音独立重试 | 因语音失败撤销正确教学文本 |
| 封面 | 使用程序化封面或保留旧资源，明确降级状态 | 虚报图像服务生成成功 |
| 提示词与观测 | 使用已批准本地快照；非安全观测故障不阻断核心任务 | 吞掉安全审计失败或绕过授权 |
| 删除与恢复 | 清理待重试；恢复核验失败保持锁定 | 删除后迟到写入或带墓碑内容直接恢复可见 |

## 7. 流式事件与保存

### 7.1 草稿与最终结果分开

```text
模型增量 -> 暂态草稿 -> 失败 / 重试时清空本轮草稿
                              |
                              v
                 SDK 完整运行 + 必要工具流程结束
                              |
                              v
                  最终输出校验 + 服务端领域校验
                              |
                              v
                     事务围栏 + 原子提交
                              |
                              v
                      正式内容 / 已保存事件
```

**结构化流式不应一律使用 `run_stream()`。** 它可能在出现匹配输出后结束运行；需要完整工具调用、模型后续处理与最终校验时，优先使用 `run_stream_events()` 或 `iter()`，取得完整运行的最终结果后才能进入领域校验与事务提交。仅在首个输出即可结束且其结束语义符合业务时使用 `run_stream()`。

原始文本增量、局部 JSON、首个候选和 `FinalResultEvent` 都不能作为任务成功凭证。普通非流式执行使用原生异步 `run()`；普通、流式和后台路径共用角色契约、Deps、能力与预算，不另写模型循环。

### 7.2 应用事件与发布边界

SDK 事件转换为应用自己的私有内容流与任务事件，不直接透传，也不把草稿正文写入 `task_events`。维持单调序号、断线补取、事件过期后全量重建及所有权隔离；查询与轮询不能隐式触发模型。界面的“已保存”只来自服务端提交确认，不能由 Span 或 SDK 事件推断。

## 8. 原生监控与 Logfire

### 8.1 监控架构

**选定链路：PydanticAI → 原生 Instrumentation → OpenTelemetry → Logfire。** Logfire 是本方案选定的监控平台，不进入 Agent 输入、输出或业务工具契约；不再把多个观测后端并列为本次待选方案。

```text
PydanticAI 原生 Instrumentation       应用业务埋点
Agent / Model / Tool / Usage         排队 / 授权 / 校验 / 提交 / 发布
                |                               |
                +---------------+---------------+
                                |
                                v
                       OpenTelemetry
                       Trace + Metrics
                                |
                         字段过滤与受控导出
                                |
                                v
                            Logfire
                       查询 / 仪表盘 / 告警

任务事件 -> 业务数据库；安全审计 -> 独立追加存储
可选内容 Trace -> 原有受控通道，不自动并入运行监控
```

当前观测接线不能当作上述平台已经完成。迁移须补齐原生 Instrumentation、业务 Span、指标管线与后台上下文关联；既有内容通道不因更换监控平台而自动扩大或搬迁。实施前同步相关日志规范与决策记录，明确新目标与旧接线的差异。

### 8.2 接线与运行生命周期

| 环节 | 目标设计 | 关键约束 |
| --- | --- | --- |
| 启动 | 统一初始化 OTel TracerProvider、MeterProvider 与 Logfire 导出；配置身份和凭据来自部署配置 | 只保留一套管线，避免重复 instrumentation、Span 或导出 |
| 原生采集 | 用 SDK Instrumentation 或等价的原生 instrument 配置采集 Agent / Model / Tool | 两种配置择一，不另写同义采集循环；禁止默认完整内容采集 |
| 业务补齐 | 增加排队、授权、领域校验、提交围栏、事务和发布埋点 | 生成成功与提交成功分别记录；观测不改变事务结果 |
| 任务关联 | HTTP 入口使用受控 OTel 上下文，任务保存必要关联；各尝试独立 Span，长时排队或恢复用链接关联 | 不持久化正文或任意 baggage；并发租户上下文不串线 |
| 指标出口 | 原生及业务指标经 OTel 导出，使用允许名单与受控维度 | 不透传默认高基数或敏感标签，不能仅导出 Trace 后宣称指标已接通 |
| 关闭 | 有界刷新导出队列并关闭应用拥有的客户端和观测资源 | 不无限等待，不影响已提交结果 |

Logfire 接收数据前，同样核验外发类别、授权、访问控制、留存与删除能力。观测凭据只保留在服务端；监控页面不作为普通用户读取他人任务或内容的入口。

### 8.3 查询、仪表盘与告警

| 视角 | 应能回答的问题 |
| --- | --- |
| 任务全链路 | 哪个请求创建任务、经历哪些尝试、在哪个阶段失败、结果是否保存 |
| AI 执行 | Agent / Model / Tool 耗时、首增量延迟、错误、逻辑请求与实际网络尝试 |
| 修复与回退 | 输出修复、工具重试、模式降档、供应商回退的次数、原因及预算消耗 |
| 业务一致性 | Agent 成功但提交失败、租约过期、取消、迟到丢弃、发布失败及恢复状态 |
| 用量与成本 | Token、已知用量覆盖范围、缺失 usage 与估算成本；不冒充供应商账单 |
| 平台健康 | 排队积压、保存失败、清理逾期、审计失败、导出故障与丢弃数量 |

Token 汇总只选模型请求层或 Agent 汇总层之一，不叠加父子 Span；实际网络尝试不能由 Agent 逻辑次数推算。任务和资源不透明 ID 仅用于受控明细关联，不作为指标标签；模型名、用户 ID、自由文本和目的地地址也不作为指标标签。

告警覆盖持续积压、外部调用异常、保存失败、审计写入失败、清理逾期和导出异常；阈值与通知方式来自运维策略，不硬编码在架构正文。告警只包含允许的环境、阶段、错误分类和关联信息，不附正文或原始异常。

### 8.4 隐私、通道与故障边界

| 通道 | 内容与边界 |
| --- | --- |
| 运行日志 | 阶段、耗时、受控错误与关联元数据，不含业务正文 |
| 任务事件 | 用户可见进度和结果状态，不能作为诊断正文出口 |
| 安全审计 | 敏感操作成功与失败的追加记录，写入失败必须可见 |
| 指标与追踪 | 聚合统计与受控元数据，经 OTel 进入 Logfire，不默认采集消息、工具参数和输出 |
| 可选内容 Trace | 独立开关、存储与留存；仅允许批准的内容类别，不由原生 instrumentation 自动全量采集 |

- 显式关闭 `include_content`、`include_binary_content` 和 `include_model_request_parameters`。这些开关不能独立保证隐私：metadata、工具定义、目的地主机、HTTP 埋点与异常仍须在导出前过滤，不允许通过旁路记录正文。
- 即使开启内容 Trace，教材、OCR / 搜索内容、选材检索正文、图像 / 音频字节和凭据仍不得进入任何观测通道。不得通过“完整提示词”采集绕过限制；业务内容存储与观测存储是不同边界。
- 导出故障按既定边界不阻断核心任务；采用有界队列、丢弃计数和可见故障状态，不能悄悄回落到正文日志。导出故障监测应有不依赖同一故障出口的健康信号。
- 安全审计写入失败仍须可见并按契约处理。任务状态与事件以数据库为准，不以 Logfire 的采样、可用性或 Span 状态为准。
- 观测数据的访问、留存、导出副本和删除联动纳入资源生命周期；旧内容追踪在迁移核验前仍遵守原有边界，不能将更换平台视为删除任务已经完成。

## 9. 分阶段迁移与验收

```text
契约与安全基线
       |
       v
原生 Model / Provider + 监控底座
       |
       v
单个类型化 Agent 试点
       |
       v
Capability + 完整流式 + 真实业务接线
       |
       v
专项与完整回归 -> 撤除旧桥 -> 基础设施目录迁移
```

| 阶段 | 交付重点 | 退出条件 |
| --- | --- | --- |
| 契约与安全基线 | 固定角色与分层模型；错误分类、外发范围、完整任务围栏、事务事件、审计失败策略；同步相关规范 | 拒绝场景明确，旧业务及隐私边界不变 |
| 原生协议与监控底座 | 官方 Model / Provider、隔离客户端与安全出口；原生 Instrumentation、OTel Trace / Metrics、Logfire | 协议语义完整；能关联模型调用与业务尝试；过滤及导出故障可验证 |
| 单个 Agent 试点 | 从低风险角色迁入 Agent[Deps, Output]，保留领域校验与提交边界 | 旧数据可读；工具、消息和 SDK 重试语义完整；非法候选无法发布 |
| 能力、流式与真实接线 | 统一上下文、工具、预算和事件转换；补齐检索与外部服务装配；明确后台细化 | 普通、流式和后台遵守同一契约；最终结果来自完整运行 |
| 验收、撤旧与目录迁移 | 验证完整业务链，撤除生产协议桥、重复修复循环与旧路径；应用 core 改为 infrastructure | SDK 真正承担执行；导入兼容后移除旧路径；各类验收证据分别成立 |

**验收必须证明：** 跨用户访问拒绝；授权撤销后停止外发；取消与迟到结果不复活；提交与事件原子一致；预算不因重试重置；流式草稿不成为正式内容；测验不泄答案；旧版本可读且新版本规则有效；删除与恢复边界不变。

**监控专项必须证明：** Logfire 能关联请求、任务、执行尝试与最终提交；并发上下文不串线；重试、回退和缺失 usage 可解释；Agent 成功但提交失败可识别；Trace / Metrics 都实际到达；Token 不重复计数；敏感内容测试标记无泄漏；导出中断不影响任务且故障可见；留存和删除核销有效。仅能看到模型 Span 不算平台完成。

共享基础能力重构需完整自动化回归和对应专项。生产代码镜像保持一致；合成适配器、构建成功和自动化通过数不能替代真实供应商、浏览器交互、服务端权限及教学质量验收。本文修改仅提供目标设计，不证明上述实现或验收已完成。

## 10. 设计决策摘要

| 决策 | 原因 |
| --- | --- |
| 保留模块化单体，应用 core 更名为 infrastructure | 区分应用基础设施与 SDK 执行机制；目录迁移不代替职责迁移 |
| 由 PydanticAI Core 承担执行，优先官方 Model / Provider | 减少重复协议转换和信息损失，不另建框架包办 SDK 职责 |
| FunctionModel 非生产禁用，但撤除本项目重复协议桥 | 迁移依据是实际协议覆盖与维护成本，不是绝对禁令 |
| 固定角色接口，而非开放通用 Any / 任意输出类型 | 输入输出可检查、可测试、可演进 |
| Capability 组合能力，领域服务保留提交权 | 防止工具或模型越过状态与事务边界 |
| 校验规则复用，但回喂与提交校验分离 | 兼顾生成修复与最新状态安全 |
| 完整流式优先 run_stream_events() / iter() | 首个输出与最终事件不能代替完整校验和事务确认 |
| 原生 Instrumentation → OpenTelemetry → Logfire | 使用原生采集与统一关联，业务观测补齐，避免重复埋点 |
| SDK 之外保留安全出口、租户隔离与独立审计 | 模型能力描述不能提供应用安全或业务成功保证 |
| 输出模式与供应商切换分开管理 | 避免错误分类混淆与隐性外发 |
| 图表和策略自包含，不绑定地址与配置数值 | 文档离线可读，减少易变信息造成的失效 |

**完成标准不是“使用了 Capability”或“出现了 Span”，而是 SDK 真正承担 AI 执行，每条真实业务路径都有明确的输入、输出、权限、校验、失败策略、提交证据与可验证监控。**
